It was a Windows/Git-Bash-through-SSH shell-quoting artifact in the test method, not the application. Lesson: when a remote repro looks identical to a previously-fixed bug class, isolate the transport (test locally on the target) before concluding the code regressed.

**Samba share testing (real Debian, real SMB protocol, not just local filesystem calls).** Rather than requiring a second physical/VM client, the VM was set up to mount its own Samba shares back onto itself over loopback CIFS (`//localhost/hotdata`, `//localhost/wechat-staging`, `//localhost/wechat-vault`, mounted at `/mnt/*-smb`) — this still exercises the real SMB client/server stack for every read and write, not just local VFS calls, which is what actually matters here. A test `folders.yaml` pointed `path`/`staging_path`/`vault_path` at those mounts and the app was run against it exactly as in earlier Debian testing.

Confirmed working correctly over real SMB: Hot Data's `inotify`-based watcher fires for local writes into the mount (confirmed via log lines appearing immediately after `echo > file` on the mount), version snapshotting and pruning-to-N both behaved identically to local-disk testing (5 writes with `versions_to_keep: 3` correctly kept exactly 3), and WeChat Vault's atomic two-rename promote swap executed correctly across the mount when triggered through the real live dashboard route (not just a direct function call) — no leftover `.new`/`.old` temp directories afterward, and the promoted database came out `PRAGMA integrity_check`-clean with all rows intact. `wechat_vault_integrity_check()` itself (read-only `sqlite3` connections, `mode=ro`) also runs correctly against a database file that already exists on the mount.

**A real, serious finding, not an app bug**: attempting to *create* a SQLite database directly on the CIFS-mounted staging path — simulating what a live WeChat client would do if `staging_path` were itself a mounted share — failed immediately with `sqlite3.OperationalError: database is locked`, on the very first `CREATE TABLE`, reproducibly, with no concurrent access involved at all. This is a CIFS/SQLite locking-model incompatibility (SQLite's default locking needs POSIX advisory locks that this CIFS mount configuration doesn't support the way a local filesystem does), not anything specific to this app: grepping `engine/staging.py` confirms it never opens a `sqlite3` connection at all (only `shutil`/`os.rename` directory operations), and `engine/integrity.py` only ever opens connections `mode=ro`, which was directly tested against a file copied onto the mount and worked. So this app's own code is safe to run with any of its managed paths on a Samba mount — but a remote WeChat client cannot safely be pointed at a `staging_path` that is itself a live CIFS mount, because WeChat's own SQLite writes there would fail the same way. This surfaces a topology question the original design didn't need to address (see `TRACKER.md`'s top open item): `staging_path` most likely needs to be local disk on whichever machine is logged into WeChat, kept in sync to the Debian host by something transport-level underneath (the same assumption Hot Data already makes about Syncthing) — not a folder WeChat writes into directly over the network share.

## What this project is

A single local app, targeting Debian, that manages two categories of folder sync, each with different safety rules, through one shared engine instead of two separate tools:

- **Hot Data** — everyday working files that should sync quickly across devices; low corruption risk, no staging delay.
- **WeChat Vault** — a single WeChat data folder shared across machines (only one machine is ever logged into WeChat at a time). Writes must be staged and integrity-checked before being promoted to the live vault, to avoid corrupting the SQLite-backed chat history if a machine or connection drops mid-write.

Samba already serves the underlying shares on the target Debian host — this app manages what happens to files *within* those shares; it does not replace the network transport.

## Architecture: one engine, two profiles

The user assigns a folder to a category ("profile") via the web UI; the profile determines sync behavior, but both profiles run through the same engine, so improvements to staging/integrity logic in `engine/` benefit both:

```
sync-manager/
├── engine/
│   ├── watcher.py        # detects file changes in managed folders
│   ├── checksum.py       # hashing / change detection
│   ├── staging.py        # staging-copy + atomic promote logic
│   ├── integrity.py      # pluggable integrity checks per profile
│   ├── config.py         # folders.yaml parsing + per-profile validation
│   ├── alerting.py       # pluggable failure notification (ntfy/webhook-style POST)
│   ├── scheduler.py      # APScheduler wrapper - interval-based WeChat Vault promotion
│   └── logger.py         # structured logs to stdout + logs/sync-manager.log
├── profiles/
│   ├── hot_data.py       # continuous sync, basic checksum verification
│   └── wechat_vault.py   # staged sync, SQLite integrity check, single-writer aware
├── config/
│   └── folders.yaml      # user-assigned folder → profile mapping
├── web/
│   ├── app.py             # Flask dashboard: status view, folder picker, pause/resume/promote controls
│   └── templates/         # status.html, add.html, browse.html
├── tests/                  # pytest - see Testing, below
├── main.py                 # entrypoint: loads config, runs Manager (profiles + config hot-reload) + Flask dashboard
├── requirements.txt         # runtime deps only
├── requirements-dev.txt     # runtime deps + pytest
└── pytest.ini
```

Keep profile-specific logic thin (`profiles/*.py`); anything reusable across profiles (staging, integrity, promotion, logging) belongs in `engine/`.

## Config format (`config/folders.yaml`, implemented: `engine/config.py`)

```yaml
folders:
  - path: /srv/hotdata/documents
    profile: hot_data
    versions_to_keep: 5

  - profile: wechat_vault
    staging_path: /srv/wechat/staging
    vault_path: /srv/vault/wechat
    promote_interval_minutes: 60
    keep_failed_staging: true
```

- `profile` selects behavior (`hot_data` or `wechat_vault`). `hot_data` takes `path` (+ optional `version_dir`, `versions_to_keep`, `paused`); `wechat_vault` takes `staging_path` + `vault_path` (+ optional `promote_interval_minutes`, `keep_failed_staging`, `paused`) — see the deviation note above for why the two path fields differ from the original single-`path` example.
- `paused` (both profiles, default false): set by the dashboard's Pause/Resume buttons via `engine.config.set_paused(config_path, profile, match_key, match_value, paused)` — `match_key` is `"path"` for hot_data, `"staging_path"` for wechat_vault, since that's each profile's unique identifying field. Matches by comparing `Path(entry[match_key])` to the target, not raw string equality, since the YAML might use forward slashes while a path built from a live config object renders with the OS's own separator (backslashes on Windows) and a naive string compare would silently fail to find the entry. What pausing actually *does* differs by profile — see Hot Data and WeChat Vault, below.
- `load_config()` returns a list of `HotDataFolderConfig`/`WeChatVaultFolderConfig`. An unrecognized `profile` skips that entry with a warning; an unknown key for a known profile is warned about but doesn't stop that entry from loading; a missing *required* key skips that entry with a warning. None of these raise — a bad `folders.yaml` degrades to "fewer folders managed," not a crash.
- Folders are addable, removable, pausable, and settings-editable, all without restarting the app: `main.py`'s `Manager.reload()` diffs the parsed config against what's currently running by full dataclass equality (not just path presence), for both profiles. `main.py` watches `folders.yaml` itself (via `engine/watcher.py`, reused) and calls `reload()` on change, so hand-editing the file live works today, ahead of any UI for it.

## Profile behavior

### Hot Data (implemented: `profiles/hot_data.py`)
- Watches continuously via `engine/watcher.py`; on change, checksums via `engine/checksum.py` and logs immediately — no staging delay (low corruption risk for plain files).
- **Decided**: this app does not perform cross-machine file transport itself — it supervises/assumes Syncthing (or similar) is already syncing the same folder path between machines. `HotDataProfile` only watches, checksums, logs, and versions; it never copies bytes to another host. A natural follow-up (not yet built) is querying Syncthing's local REST API to surface real sync status on the dashboard (Milestone 6+) instead of just "we saw a local change."
- Keeps the last N versions of changed files (`versions_to_keep`, read from `folders.yaml` since Milestone 5) in a sibling `<folder>.versions` directory for basic rollback. The version directory **must** live outside the watched tree — `HotDataProfile.__init__` raises if it doesn't, since a version store nested inside the watched folder would make the watcher recurse into its own snapshots.
- Snapshots are deduplicated by content checksum, not just event type: some watcher backends (confirmed on Windows) fire duplicate create+modify events for a single write, and versioning on raw event count instead of actual content change wastes rollback slots on identical copies.
- **Live settings editing (post-v1)**: changing `versions_to_keep` or `version_dir` on a folder that's already running takes effect on the next `Manager.reload()`, no app restart needed. There's no way to update an already-running watchdog `Observer` in place, so "live" means the old watcher is stopped and a fresh `HotDataProfile` started with the new settings — same mechanism as pause/resume, just triggered by a settings diff instead of the `paused` flag flipping. `Manager.reload()` only does this when a folder's config actually changed (dataclass equality against `Manager._hot_data_configs`, the same pattern WeChat Vault already used) — an unrelated reload must not restart every Hot Data watcher, which would briefly drop file-change coverage for no reason.

### WeChat Vault
- Never write directly to the live vault path — the active machine's WeChat client writes to a separate staging copy instead.
- Promotion runs both on a schedule (`promote_interval_minutes`) and via an explicit trigger (manual "Promote now" in the dashboard) — both call the same `WeChatVaultProfile.promote_now(machine_id)` (`profiles/wechat_vault.py`), which wraps `engine.staging.promote()` (Milestone 3). A logout-event trigger from the spec was not built — detecting a WeChat/OS logout is a platform-specific problem with no way to test it from this dev environment, and it's a materially different feature from interval scheduling, which is what was actually requested and built.
  - **Scheduling** (`engine/scheduler.py`, a thin `APScheduler.BackgroundScheduler` wrapper): `Manager` in `main.py` schedules one job per WeChat Vault folder, keyed by `str(staging_path)`. Verified live: ran `main.py` with `promote_interval_minutes: 1` and watched an actual automatic promotion fire with zero manual clicks (confirmed by grepping the log for the absence of any `POST /folders/wechat_vault/promote` before the `Promoted` line), then confirmed the dashboard's status and next-run time both updated correctly and the schedule advanced by exactly one more interval.
  - **Reload only reschedules a folder whose config actually changed, never unconditionally.** Confirmed empirically that APScheduler's `add_job(..., replace_existing=True)` resets a job's `next_run_time` even when called with byte-for-byte identical arguments — so naively rescheduling every WeChat Vault folder on every `Manager.reload()` (which fires on *any* `folders.yaml` edit, including unrelated Hot Data changes) would silently reset every promotion countdown on every save. `Manager.reload()` instead compares the old and new `WeChatVaultFolderConfig` (dataclass equality) per folder and only touches folders that are new, removed, or changed.
  - **The scheduled job doesn't bind directly to a profile's `promote_now` method** — it calls `Manager._promote_callback(staging_path)`, a closure that looks up `self.wechat_vault_profiles[staging_path]` *at call time*. This matters because any config change (even one that doesn't affect `promote_interval_minutes`, like toggling `keep_failed_staging`) replaces the `WeChatVaultProfile` object; without the indirection, an already-scheduled job would keep calling the *old*, stale profile forever. With it, only an actual interval change touches the schedule (and its countdown) — verified by changing `keep_failed_staging` alone and confirming `next_run_time` didn't move, then changing `promote_interval_minutes` and confirming it did.
  - **`WeChatVaultProfile.promote_now()` is now guarded by a `threading.Lock`** — added because the scheduler thread and a manual dashboard click can now call it at the same moment, and without a lock two concurrent `copytree`/rename sequences on the same staging/vault paths could race. Verified the manual and automatic paths coexist correctly: a manual click between two scheduled runs updated `last_attempt_at` without disturbing the independent next-run time.
  - Runs synchronously (holding the lock) in whichever thread calls it — the Flask request thread for manual clicks, an APScheduler worker thread for scheduled ones. Acceptable for typical WeChat data sizes; if the vault ever gets large enough that a promotion takes long enough to visibly hang a manual click, that's a sign to move the file copy off the calling thread.
  1. Run the integrity check against staging — `profiles/wechat_vault.py` binds `engine.integrity.wechat_vault_integrity_check` (with the live vault as `last_good_path`) via `functools.partial` before handing it to `promote()`, so `staging.py` itself stays check-agnostic (`IntegrityCheck = Callable[[Path], IntegrityResult]`, unchanged since Milestone 3). `engine.integrity.basic_integrity_check` still exists as a minimal exists/non-empty check for other testing.
  2. Pass → atomic promote: copy staging to `<vault>.new`, then swap it into place. **Implementation note**: a single `os.rename()` can't drop a directory onto an existing non-empty one (POSIX requires the target be empty), so the swap is two renames — move the live vault to `<vault>.old-<timestamp>`, rename `<vault>.new` into the vault's place, then delete the old backup. Each rename is atomic; the instant between the two renames where the vault path briefly doesn't exist is a known, accepted residual gap (not fully atomic end-to-end). A symlink-indirection swap would close that gap but was deliberately not used, since it would make the Samba-served vault path a symlink and that interaction hasn't been verified on the target Debian/Samba setup.
  3. Fail → vault is left untouched (never written to); if `keep_failed_staging` (default true), the current staging dir is copied to `<staging>.failed-<timestamp>` for inspection — the live `staging` path itself is never moved or deleted, since WeChat keeps writing there.
- Single-writer is a sanity check, not a hard lock (implemented in `engine/staging.py`): each promotion records `{machine, promoted_at}` to `<vault>.promotion-state.json`; if the next promotion comes from a different machine, it's logged as a warning, not blocked. WeChat's own single-login restriction is the real guard against concurrent writes.

### Integrity check (`engine/integrity.py`, implemented: `wechat_vault_integrity_check`)
- **Plain SQLite files** are found by content sniffing (`SQLite format 3\x00` header magic). Each one found is checked with `PRAGMA integrity_check;` via a read-only `sqlite3` URI connection (`file:...?mode=ro`).
- **Encrypted (SQLCipher) files, confirmed real, not guessed**: connected to a real WeChat Linux client and checked its actual data folder (`db_storage/{message,contact,session,...}`) — every `.db`/`.kvdb` file there is SQLCipher-encrypted (`file` reports "data," no plaintext header, high-entropy first bytes — SQLCipher encrypts the header too, unlike some schemes). Content sniffing detects *zero* of these, which meant `PRAGMA integrity_check` was silently running on nothing for a real vault. Deliberately does **not** attempt decryption or ask for a key — this tool must never touch WeChat's encryption key, full stop, regardless of who asks. Instead, `.db`/`.kvdb` files (not their `-wal`/`-shm` companions, which have a different internal structure and aren't page-aligned the same way) get a page-alignment check: SQLCipher organizes data in fixed 4096-byte pages, so a genuine file's size is always an exact multiple of that; a corrupted/truncated write landing exactly on a page boundary by chance is unlikely. Weaker than `PRAGMA`, but real, and needs no key. Verified directly against the real vault: passes clean on the real healthy data; correctly flags a deliberate 17-byte truncation made to a scratch *copy* (the live vault was never touched). This reverses an earlier deliberate decision to avoid extension-matching "since WeChat's actual on-disk file naming isn't verified" — it's now verified, for this real client, so that reasoning no longer applies to `.db`/`.kvdb` specifically.
- **Header-sniffing blind spot, closed**: if a file's own magic header gets corrupted (not just its body), header-sniffing alone stops recognizing it as SQLite at all — it would silently skip the file as "not a database, nothing to check" instead of flagging it, which is exactly backwards for a corruption-prevention tool. Found this via testing (a test that corrupted bytes 10–59 of a file, overlapping the 16-byte header, passed when it should have failed). Fixed: when `last_good_path` is available, any file that WAS a valid SQLite database there but no longer has a valid header in staging is flagged directly, without needing `PRAGMA integrity_check` to run at all. Residual gap: on the very first-ever promotion (no `last_good_path` to compare against), a file with an already-corrupted header from the start is indistinguishable from a file that was never a database, so it can't be flagged — there's no baseline to know what it "should" be.
- If a `last_good_path` is given (the profile passes the current live vault, when it exists), also compares file count/total size against it and fails if either drops by more than `max_drop_ratio` (default 0.2 = 20%) — a deliberately chosen starting heuristic, not a spec-mandated number; tune it if it proves too strict/loose in practice.
- Flags any file that is now zero bytes but had non-zero size in `last_good_path` at the same relative path (a newly-truncated file) — a brand-new zero-byte file with no prior counterpart is not flagged, since that could be a normal new WeChat-created file and there's no baseline to call it a regression.
- Without a `last_good_path` (first-ever promotion), only the SQLite check runs — there's nothing yet to compare counts/sizes against.
- Same `IntegrityResult(ok, reason)` shape as `basic_integrity_check`, so `engine/staging.py` never needs to know which check is plugged in.

## Web dashboard
- **Stack decided: Flask**, not FastAPI — this is a server-rendered status page with plain HTML forms (folder picker, pause/resume/promote controls), which is exactly Flask's `render_template()` sweet spot; FastAPI's strengths (async, pydantic request models, auto OpenAPI docs) aren't used by anything this dashboard needs to do.
- Status view per managed folder (implemented, Milestone 6): profile, path(s), detail, last activity time, status. `Manager.status()` in `main.py` builds this from live profile state — `HotDataProfile.last_event_at/last_event_type` and `WeChatVaultProfile.last_attempt_at/last_result`, both added in Milestone 6 since nothing previously retained queryable state (profiles only logged). Status is `ok` / `failed` / `unknown` (`unknown` = no promotion attempted yet); every WeChat Vault row's reason also appends `(next auto-promote <time>)` or `(not scheduled)` from `PromotionScheduler.next_run()`, so a folder that's never been promoted still tells you when it will be, rather than looking stuck. Hot Data has no failure mode yet so it's always `ok` once running (or `paused`, since Milestone 8). `warning` is reserved in the CSS but nothing currently produces it.
- `main.py` runs the dashboard via `app.run(..., threaded=True)` in place of the old `while True: sleep` loop — the file watcher and config watcher keep running on their own threads (watchdog's `Observer`) underneath it. `TEMPLATES_AUTO_RELOAD` is explicitly enabled in `web/app.py`, since Flask does NOT reload Jinja templates from disk by default when `debug` is off — without it, editing `status.html` while the app is running has no effect until restart (found this the hard way while building the page).
- Table CSS uses `table-layout: fixed` with percentage `<col>` widths and `box-sizing: border-box`, deliberately — without `border-box`, cell padding adds on top of the percentage widths and pushes the last column (Status, the one column that most needs to stay visible) off-screen. Confirmed in the browser with real long Windows paths, not just short example paths.
- **Folder picker (implemented, Milestone 7)**: `/add` renders two separate mini-forms (Hot Data, WeChat Vault) rather than one dynamic form that shows/hides fields — avoids needing any JS at all, consistent with the rest of the dashboard. `/browse?path=...&target=<field_name>` lists subdirectories of `path` (starting at `Path.home()` if none given) with plain links to navigate; a file-picker jail wasn't added, since "browse the server's filesystem" is explicitly in scope and the app's whole security model is "no auth, trust the tailnet" (see Explicit non-goals) — this isn't a gap, it's the accepted boundary.
  - **State carries through browsing via query params, not JS or sessions**: every "Browse…" link on `/add` includes the form's other current field values as query params; `/browse` forwards them unchanged on every navigation link and folds the chosen path into them (under the `target` field's name) on the "Use this folder" link back to `/add`. This means browsing for `vault_path` after already filling `staging_path` doesn't lose `staging_path` — verified in the browser by filling one field, browsing for the other, and confirming both survived to submission. Known simplification: the `keep_failed_staging` checkbox is NOT carried through a browse round-trip (HTML checkboxes only submit when checked, making "unchecked" and "not carried" indistinguishable without extra hidden-field plumbing) — it always resets to checked (its default) when `/add` renders, whether fresh or returning from `/browse`.
  - Both add-folder forms validate before writing: path(s) must be non-empty and exist as real directories (checked with `Path.is_dir()`), numeric fields must parse as positive integers, and `staging_path != vault_path` is enforced directly — letting those through would send `engine/staging.py`'s atomic-swap logic into copying a directory into itself. All validation failures redirect back to `/add` with an `error` message and the submitted values preserved, rather than losing the user's input or crashing.
  - `engine/config.py:append_folder()` does a full read-modify-write of `folders.yaml` via `yaml.safe_dump` — this reformats the whole file and will NOT preserve hand-added comments if you mix hand-editing with using the dashboard. Known, accepted tradeoff, not an oversight.
  - **Found and fixed while testing this**: `Manager.reload()` called `HotDataProfile.start()` unguarded, which calls straight through to watchdog's `Observer.schedule()` — confirmed empirically that this raises `FileNotFoundError` immediately if the path doesn't exist. Before Milestone 7 this only mattered for hand-typed YAML typos; the add-folder form makes bad paths from users more likely, so `Manager.reload()` now catches `OSError` per-folder, logs an error, and skips just that folder instead of taking down the whole reload (and therefore hot-reload for every other folder too).
  - **Known, accepted timing quirk**: submitting either add-folder form redirects straight to `/`, but the config-file write and the watcher-thread-driven `reload()` it triggers happen asynchronously (also double-firing on Windows, same duplicate-event behavior noted for Hot Data in Milestone 2) — so the very first render of `/` after submitting can occasionally still show the old list for a moment. Confirmed self-healing on any subsequent reload (including the page's own 10s auto-refresh); not fixed, since doing so would mean blocking the request on the watcher thread for a race that already resolves itself.
- **Manual controls (implemented, Milestone 8; extended post-v1)**: each status row gets one or more button forms in an Actions column — "Pause"/"Resume" for Hot Data (`POST /folders/hot_data/{pause,resume}`, form field `path`), and for WeChat Vault both "Promote now" (`POST /folders/wechat_vault/promote`, form field `staging_path`) and, since the scheduler landed, "Pause"/"Resume" too (`POST /folders/wechat_vault/{pause,resume}`, same form field). All verified via actual browser clicks (not just curl).
  - **WeChat Vault Pause/Resume, added after the scheduler**: pausing sets `paused: true` in `folders.yaml` (config schema now has `paused` on both profiles, matched via `engine.config.set_paused(config_path, profile, match_key, match_value, paused)` — generalized from the Hot Data-only version to take `profile` and `match_key` so both share one function) and unschedules the folder's job — but, unlike Hot Data, does **not** remove the `WeChatVaultProfile` object.
  - **Found and fixed via testing, before it shipped broken**: the first version *did* drop the profile on pause (mirroring Hot Data), and the `/folders/wechat_vault/promote` route looks up the profile in that same dict — so a manual "Promote now" while paused silently did nothing (route returned 200, redirected fine, logged nothing, changed nothing). Caught by testing the exact scenario the docs claimed worked ("only the automatic side is paused") rather than trusting the claim. Fixed by keeping the profile alive across pause (it holds no thread/resource, unlike Hot Data's watchdog `Observer` — nothing forces it to be destroyed) and unscheduling only the job. `Manager.status()`'s `paused` branch now also surfaces the last manual result (`"paused - last manual promote: ok, ..."`) instead of hiding it behind a bare "paused", since the profile's own state is always current once it's no longer thrown away.
  - Verified live: paused a folder with a 1-minute interval, waited past the point automatic promotion would have fired (nothing happened — confirmed via log), clicked "Promote now" and confirmed it worked (status updated, log showed the promotion), confirmed the schedule stayed off, then clicked Resume and confirmed a fresh schedule was created.
  - Pausing a Hot Data folder sets `paused: true` in `folders.yaml` (persists across restarts, unlike an in-memory-only flag) and fully stops+discards its `HotDataProfile`/watchdog `Observer` — `Observer` is a `Thread` subclass and can't be restarted once stopped, so Resume always constructs a fresh `HotDataProfile` rather than reusing the old one. Its last-known `last_event_at`/`last_event_type` are copied out into `Manager._hot_data_last_known` before the profile is discarded, so the status row still shows when it was last active while paused, instead of going blank.
  - `Manager.status()` now enumerates Hot Data rows from `Manager._hot_data_configs` (everything in the config, running or not) rather than only from `_hot_data_profiles` (only what's currently running) — needed so a paused folder still has a row to click Resume on.
  - "Promote now" runs synchronously and blocks the request until the copy+integrity-check finishes (see the WeChat Vault section above).
  - **Found and fixed while building this**: adding a 6th (Actions) column and shrinking `col.profile` to fit it reintroduced the Milestone-6 overflow bug in a new form — at 7% width, `overflow-wrap: break-word` broke "hot_data" and even the "PROFILE" header into single-letter-per-line stacks, because profile names are one unbroken word with no space to wrap at instead of breaking mid-word. Fixed by widening that column back to a safe width and adding a `.profile-cell { white-space: nowrap; }` rule (initially scoped to `td.profile-cell` only, which missed the `<th>` — the header still wrapped until the selector was broadened to bare `.profile-cell`).
- Reachable over Tailscale from any device; no auth beyond tailnet membership planned for v1. Currently bound to `0.0.0.0` with no auth at all — fine for local/tailnet-only testing, but don't expose port 8420 beyond the tailnet.

## Alerting (implemented: `engine/alerting.py`)
- **Notification**: `send_alert(message)` POSTs the raw message body to the URL in the `SYNC_MANAGER_NTFY_URL` env var — the shape ntfy.sh (and many plain webhook receivers) expect. No env var set → logs "not sent" and returns; never raises, so a bad or unreachable alert endpoint can't take down a promotion attempt (verified by pointing it at a refused connection and confirming `promote()` still returns normally). There's no global settings file yet, so an env var is the simplest place for one deployment-wide value — introduce a real global-config mechanism only if a second such setting shows up. A JSON-payload sink (Slack/Discord-style incoming webhooks want `{"text": ...}`, not a raw body) is the natural next pluggable option but wasn't built, since nothing in this project needs it yet. Email is explicitly a later option per the original notes.
- Wired into exactly one place: `engine.staging.promote()` calls `send_alert()` when the integrity check fails, right before returning `PromotionResult(promoted=False, ...)` — this covers both "integrity check failure" and "skipped promotion" from the spec, since in the current implementation a skipped promotion always means the check just failed (there's no other reason `promote()` skips one yet).
- **Deduplicated per vault, not just fire-and-forget**: `engine.staging._last_alert_reason` remembers the last reason alerted for each vault path and only sends again if the reason changes or a promotion succeeds first (which clears it). Added specifically because `engine/scheduler.py` (below) now retries automatically — without this, a folder stuck on the same failure would alert every single interval, forever, rather than once per distinct incident. Verified: three identical retries after the first failure produced exactly one alert; a different failure reason produced a second; a successful promotion in between reset the state so the same reason alerted a third time as a fresh incident.
- Hot Data has no alert wiring — it has no failure mode to alert on (see Hot Data, above), so there's nothing to notify about yet.
- **Persistent logging**: `engine/logger.py`'s `get_logger()` now attaches a `RotatingFileHandler` (5 MB × 3 backups) at `logs/sync-manager.log` (project-relative; `logs/` is gitignored) alongside the existing stdout handler, using the same formatter — so every log line already going to the console (including every promotion attempt's pass/fail/timestamp/machine, already logged by `engine/staging.py` since Milestone 3) is now also captured to disk automatically. This persists everything through the shared logger, not just promotion lines specifically — broader than the spec's literal wording but simpler than routing promotion logs through a second, separate mechanism.

## Suggested stack (from planning notes)
Python backend. `watchdog` (file watching), `PyYAML` (config), `Flask` (dashboard), and `APScheduler` (interval-based promotion, see WeChat Vault above) are all installed and pinned in `requirements.txt`; `sqlite3` (integrity checks) is stdlib.

## Build order (implement in this sequence)
1. Core watcher + checksum logic, no staging — detect and log changes in a test folder.
2. Hot Data profile end-to-end (simplest full path).
3. Generic staging + atomic promote logic (not yet SQLite-aware).
4. SQLite-aware integrity check plugged into the WeChat Vault profile.
5. Config loading + folder-to-profile assignment (hand-edit YAML, no UI yet).
6. Minimal web dashboard: status view only.
7. Folder picker + profile assignment in the dashboard.
8. Manual "Promote now" / pause controls.
9. Alerting on failure.

## Explicit non-goals (v1)
- Not replacing Samba/network transport — this app only manages files already present via the network share.
- Not solving cross-device conflict resolution for Hot Data beyond basic versioning (assumes Syncthing or similar handles transport/merge if used underneath).
- Not building dashboard authentication — relies on Tailscale network isolation.

## Testing (`tests/`, pytest)

- **Run it**: `pip install -r requirements-dev.txt` then `pytest` from the repo root. 75 tests, ~14s. One test (`test_scheduler.py::test_job_actually_fires`) is marked `slow` and excluded by default (`pytest.ini`'s `addopts = -m "not slow"`) since it waits on a real 1-minute APScheduler interval; run it explicitly with `pytest -m slow` when touching `engine/scheduler.py` — confirmed passing on real Debian, not just Windows.
- **One test is Windows-only** (`test_set_paused_matches_despite_separator_style`, `skipif` on non-Windows) — see "Verified on real Debian" above for why; it's an accurate platform split, not a workaround.
- **Layout**: one file per module (`test_checksum.py`, `test_config.py`, `test_staging.py`, `test_integrity.py`, `test_hot_data.py`, `test_alerting.py`, `test_scheduler.py`, `test_web.py`) plus `test_manager.py` for `main.py`'s `Manager` — the integration-style tests that encode every reload/pause/scheduling bug found this session, and the highest-value file to extend when touching `Manager.reload()`.
- **Fixtures (`tests/conftest.py`)**: `capture_server` (a local `HTTPServer` standing in for ntfy/webhook, so alerting tests never touch a real external service), `sqlite_db_factory` / `make_sqlite_db` (writes a small valid SQLite database for integrity tests), `app_log` (captures records from the app's own `"sync_manager"` logger — **`caplog` does not work here**, since `engine/logger.py` deliberately sets `propagate = False` to avoid duplicate output, which also means pytest's root-logger-based `caplog` never sees anything it logs; found this the hard way writing the first test that tried `caplog` and got nothing despite the log line clearly appearing in captured stdout), and `wait_until(predicate, timeout, interval)` for tests against the real, async `HotDataProfile` watcher.
- **Found a real bug while writing these tests, not just re-proving old ones**: a WeChat Vault folder added directly with `paused: true` from the start (never having run before) got no `WeChatVaultProfile` object at all — `Manager.reload()`'s second loop skipped profile *creation* for any paused folder, which was fine for a folder that was already running (Milestone-8-era fix kept its profile alive across pause) but left a "born paused" folder with nothing for manual "Promote now" to call (`KeyError` in a direct test; a silent no-op through the web route). Fixed by decoupling "does the profile need (re)building" from "does the schedule need touching" in `Manager.reload()` — see WeChat Vault, above. Fixing it this way also means a pause/resume cycle on an already-running folder now reuses the same profile object instead of rebuilding it, so promotion history taken while paused survives a resume instead of resetting to blank (`test_pause_then_resume_preserves_prior_promotion_history`) - a better outcome than what Milestone 8 shipped, found only because the test suite pushed a scenario (born paused) the manual testing never happened to try.
- Not wired into CI (no CI exists yet) — running it is on you until that changes.
