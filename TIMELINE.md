# TIMELINE.md

A short chronological log of what's been built and fixed on Sync Manager — read this first for "how far have we come," then go to `CLAUDE.md` for the technical detail behind any entry below.

**Sources**: git commit history and this project's Claude Code session history (the only two that exist for this repo — it was built from an empty directory entirely in Claude Code, so there is no separate Codex or other-agent history to draw from here, despite that being a plausible source in general).

**Event types**: `Milestone` (a build-order checkpoint reached), `Update` (something added outside the numbered build order), `Troubleshooting` (a bug found and fixed), `Decision` (a design choice made where the spec was ambiguous or silent).

**Maintaining this file**: append a new entry under today's date heading (add one if it doesn't exist yet) whenever a milestone lands, a real bug is found and fixed, or a non-obvious decision gets made — one line, no more detail than below. Full rationale belongs in `CLAUDE.md`, not here.

## 2026-09-25

- **[Milestone] Project bootstrap** — Repo was empty; `CLAUDE.md` created capturing the user's pasted design spec as the target architecture for a from-scratch build.
- **[Decision] Hot Data supervises Syncthing, doesn't sync itself** — The app only watches, checksums, versions, and logs Hot Data folders; actual cross-machine file transport is left to Syncthing (or similar) running underneath.
- **[Milestone] Milestone 1: core watcher + checksum** — `engine/watcher.py`, `checksum.py`, `logger.py`; verified live against a real test folder (create/modify/delete all logged with checksums).
- **[Milestone] Milestone 2: Hot Data profile** — `profiles/hot_data.py` adds versioned rollback (last N copies) on top of the watcher.
- **[Troubleshooting] Version pruning kept only 2 copies instead of 5** — A negative-index list-slicing bug in `_prune_versions` silently over-pruned; fixed and reverified live.
- **[Milestone] Milestone 3: staging + atomic promote** — `engine/staging.py`; a directory swap via two renames, since a single `os.rename()` can't overwrite a non-empty directory.
- **[Troubleshooting] Same-second repeat failures crashed the quarantine step** — `FileExistsError` from timestamp-collision naming; fixed with collision-safe naming (the same fix was also applied to the vault-swap's temporary backup path).
- **[Decision] WeChat Vault config needs `staging_path` + `vault_path`, not one `path`** — The original planning notes' example assumed a single path; staging and vault are independent locations that can legitimately live on different disks.
- **[Milestone] Milestone 4: SQLite integrity check + WeChat Vault profile** — Content-sniffed SQLite detection (not extension-based), `PRAGMA integrity_check`, and size/count-drop and truncation checks against the last known-good vault.
- **[Troubleshooting] A corrupted SQLite header was silently skipped instead of flagged** — Header-sniffing stopped recognizing a header-corrupted file as a database at all; fixed by cross-checking against the last known-good vault.
- **[Milestone] Milestone 5: config loading + hot-reload** — `engine/config.py` + `folders.yaml` drive a multi-folder `Manager`; folders addable/removable live without restarting the app.
- **[Milestone] Milestone 6: Flask status dashboard** — A live status table for every managed folder.
- **[Troubleshooting] Long paths pushed the Status column off-screen** — Fixed with `table-layout: fixed` + `box-sizing: border-box`.
- **[Troubleshooting] Flask wasn't picking up template edits while the app was running** — `TEMPLATES_AUTO_RELOAD` is off by default; enabled explicitly.
- **[Milestone] Milestone 7: folder picker** — `/add` + `/browse` routes, no JavaScript; form state is carried across browsing via query parameters.
- **[Troubleshooting] A bad configured path could crash the whole config reload** — `watchdog` raises immediately when asked to watch a nonexistent path; now caught per-folder so one bad entry doesn't take down hot-reload for every other folder.
- **[Milestone] Milestone 8: manual Pause/Resume/Promote controls** — Dashboard buttons for Hot Data pause/resume and WeChat Vault promote-now.
- **[Troubleshooting] The new Actions column reintroduced the Milestone 6 overflow bug** — A too-narrow Profile column broke single words onto individual letters; fixed again with a stricter `nowrap` rule.
- **[Milestone] Milestone 9: persistent logging + failure alerting** — A rotating log file, plus a pluggable ntfy/webhook-style alert on integrity failure.
- **[Update] Full v1 committed to git** — First commit (`5ce3dea`), 21 files: all 9 build-order milestones.

## 2026-09-26

- **[Update] Automatic scheduling added for WeChat Vault** — `engine/scheduler.py` (APScheduler); `promote_interval_minutes` is now actually acted on, not just parsed and ignored.
- **[Troubleshooting] Reload would have reset every promotion timer on any unrelated config edit** — Confirmed empirically that rescheduling a job resets its countdown even with identical settings; config-diffing was added before this could ship, not discovered after.
- **[Troubleshooting] Automatic retries would have alerted on every single failed attempt, forever** — Added per-vault alert deduplication so a stuck folder alerts once per distinct failure and only alerts again after a recovery or a genuinely new problem.
- **[Update] `CLAUDE.md` Handover section + this file added** — A concise orientation layer for picking the project up cold, and this chronological log.
- **[Update] Real Pause/Resume added for WeChat Vault** — Unschedules the automatic job without losing the folder's config; manual "Promote now" still works while paused.
- **[Troubleshooting] Pausing WeChat Vault silently broke manual "Promote now"** — The first version dropped the profile object on pause (mirroring Hot Data), but the promote route looks it up in that same dict — so a manual click while paused did nothing at all, with no error. Found by testing the exact claim the docs made rather than trusting it. Fixed by keeping the profile alive across pause (it holds no thread, unlike Hot Data's watcher) and only unscheduling the job.
- **[Update] pytest suite added** — `tests/` (73 tests, one module per engine/profile/web file, plus `test_manager.py` for `main.py`'s `Manager`), built retroactively from every adversarial scenario that had only lived in throwaway scripts up to this point.
- **[Troubleshooting] A WeChat Vault folder added directly as `paused: true` got no profile at all** — `Manager.reload()` skipped profile *creation*, not just scheduling, for any paused folder — fine for a folder pausing after already running, broken for one that starts paused (manual "Promote now" had nothing to call: `KeyError`/silent no-op). Found while writing `test_manual_promote_still_works_while_paused`, not by manual testing. Fixed by decoupling "does the profile need (re)building" from "does the schedule need touching" — which also means pause/resume on an already-running folder now preserves its promotion history instead of resetting it, an unplanned improvement over what shipped a few hours earlier.
- **[Update] Hot Data settings live-editing** — Changing `versions_to_keep`/`version_dir` on an already-running Hot Data folder now takes effect on the next reload (watcher stopped and restarted with the new settings), no app restart needed. Closed the last remaining item from the original "known gap" list. `Manager.reload()`'s Hot Data diffing now matches WeChat Vault's (full config equality, not just path presence) — a bug in the same family as the WeChat Vault ones above (the ordering of "read old config" vs "overwrite it") was caught and fixed while building it, before it ever ran. Two new regression tests added; full suite (75 tests) green.
- **[Milestone] First run on the actual target platform** — Everything to this point had only run on the Windows dev machine. Connected to a real Debian 13 (trixie) VM over Tailscale/SSH: full test suite (73 passed, 1 skipped, 1 slow test run explicitly and passed), a live `main.py` run with the dashboard reached from this machine over Tailscale exactly as the spec intends, and a real `inotify`-driven version snapshot confirmed on disk after writing to a watched folder.
- **[Troubleshooting] A test encoded a Windows-only assumption about path separators** — `test_set_paused_matches_despite_separator_style` asserted `C:/foo` and `C:\foo` are the same path; true on Windows (interchangeable separators), false on POSIX (backslash is just a literal character there) — surfaced as the one failure on the first real Debian test run. Not an app bug: `set_paused()`'s logic needed no change, since a real Linux `folders.yaml` only ever has forward slashes. Scoped the test to Windows-only with `skipif` rather than deleting it.
- **[Milestone] WeChat Vault promotion verified on real Debian** — Triggered a real promotion through the live dashboard route on the VM: the atomic two-rename directory swap executed on real ext4, the promoted database came out `PRAGMA integrity_check`-clean with all rows intact, no leftover temp directories, dashboard correctly showed `ok`. The highest-stakes piece of the app (the one that can lose real WeChat data if wrong) now has a real-platform confirmation, not just Windows tests.
- **[Troubleshooting] A near-miss that looked like a bug but wasn't** — An early promote test via `curl` from Windows, through SSH, to the VM sent a mangled request body and made the route silently no-op — same shape as the earlier "born paused" bug, until curling from inside the VM to its own localhost worked cleanly. Root cause was Windows/Git-Bash-through-SSH shell quoting in the test method, not the app. Recorded so the same false alarm isn't chased again.
- **[Troubleshooting] Real WeChat databases are SQLCipher-encrypted — the integrity checker detected none of them** — Checked a real WeChat Linux client's data folder: every `.db`/`.kvdb` file is encrypted (`file` reports "data," no plaintext header, high-entropy first bytes), so header-sniffing found zero recognizable databases in a real vault. `PRAGMA integrity_check` was silently running on nothing. Fixed by adding a page-alignment check (SQLCipher's fixed page size means a healthy file size is always an exact multiple of it) for files matching WeChat's now-*confirmed* real naming — deliberately not attempting decryption, since this tool must never have or ask for the key. Verified against the real vault: passes clean on real healthy data, correctly flags a deliberate 17-byte truncation on a scratch copy.
- **[Update] `TRACKER.md` added** — A live, in-place-updated status snapshot (done/not-done/blocked, priority-ranked by risk), distinct from this file's append-only history and from `CLAUDE.md`'s technical depth.
- **[Milestone] Samba share testing completed on real Debian** — Set up real `smbd`/`nmbd` shares and a loopback CIFS mount (the VM mounting its own shares back onto itself) to exercise real SMB-protocol behavior, not just local filesystem calls. Verified: Hot Data's `inotify` watcher fires correctly for local writes into a CIFS mount, version snapshotting and pruning-to-N both work unchanged; WeChat Vault's atomic two-rename promote swap executed correctly across the mount via the live dashboard route, with no leftover `.new`/`.old` temp dirs and the promoted database coming out `PRAGMA integrity_check`-clean with all rows intact.
- **[Troubleshooting] SQLite cannot open a database for writing on a CIFS mount at all — a real client-side risk, not an app bug** — Attempted to create a SQLite database directly on the CIFS-mounted staging path, simulating a WeChat client writing there live: `sqlite3.OperationalError: database is locked`, reproducibly, on the very first `CREATE TABLE`, not under any concurrent access. This app's own code never opens SQLite for writing (`engine/staging.py` only copies/renames directories; `engine/integrity.py` only opens `mode=ro` connections, confirmed unaffected by testing the actual `wechat_vault_integrity_check()` function against a file copied onto the mount) — but it means a remote WeChat client cannot safely be pointed at a `staging_path` that is itself a live Samba/CIFS mount. Recorded as an open topology decision in `TRACKER.md`, not a code fix: `staging_path` most likely needs to be local disk, synced to the Debian host by something transport-level underneath, the same assumption Hot Data already makes about Syncthing.
- **[Milestone] Persistent deployment via systemd** — `deploy/sync-manager.service` (`Restart=always`, runs as the `dane` user, no root). Installed and `enable`d on the real Debian VM; verified by `kill -9`-ing the running process directly and confirming systemd restarted it with a new PID within seconds and the dashboard was reachable again immediately after, and by `enable` registering the unit for start-on-boot.
- **[Milestone] Two real machines promoting to the same vault, verified** — Set up a second genuinely separate real machine (a macOS laptop, reachable over Tailscale — not another VM on the same host) and had it mount the Debian VM's `wechat-vault` Samba share directly (`mount_smbfs`), then ran `WeChatVaultProfile.promote_now()` from both machines in alternation, each with its own local `staging_path` (per the topology decision above), both targeting the same shared vault directory. `engine/staging.py`'s single-writer check correctly logged a warning on every switch between the two real hostnames, in both directions, without ever blocking either promotion — the first time this logic has been exercised by more than one real machine rather than by `machine_id=` arguments in a test or a single host promoting to itself twice. The vault correctly reflected whichever machine promoted most recently each time, with `PRAGMA integrity_check` staying clean throughout.
- **[Milestone] Dashboard UI for editing an existing folder's settings** — `/folders/hot_data/edit` and `/folders/wechat_vault/edit` (GET prefills from the current on-disk config, POST saves via a new `engine.config.update_folder()`, generalized from `set_paused()`'s match-by-identifying-field pattern). Each profile's identifying field (`path` for hot_data, `staging_path` for wechat_vault) is deliberately read-only in the edit form, since `Manager.reload()` diffs folders by that field — changing it there would look like removing one folder and adding an unrelated one. The `/browse` route's "Use this folder" link, previously hardcoded to always return to `/add`, was generalized with a `return_to` parameter so browsing for a new vault path from the edit form correctly returns to the edit form instead. Verified in a real browser (not just the test client): edited `versions_to_keep` on a running Hot Data folder and `vault_path`/`promote_interval_minutes`/`keep_failed_staging` on a running WeChat Vault folder, including a full round-trip through the folder-browse picker, and confirmed `folders.yaml` and the dashboard both reflected each change correctly.
- **[Troubleshooting] A stray `taskkill /F /IM python.exe` during cleanup killed every Python process on the dev machine, not just the test server** — used to stop a local dashboard test run; `/IM python.exe` matches by image name only, with no way to scope it to the PID actually started for the test. Flagged to the user immediately (4 processes had been running; all were confirmed gone afterward). Lesson: stop a specific test process by PID, never by broad image-name match, on a shared dev machine.
- **[Milestone] CI added and verified with a real run, not just plausible YAML** — `.github/workflows/tests.yml` runs `pytest` on every push/PR to `main` (`ubuntu-latest`, Python 3.11 — the closest CI proxy for the real Debian target, which also means the Windows-only test correctly skips there instead of running, matching what real Debian testing already confirmed). Pushed and watched the actual GitHub Actions run rather than trusting the workflow file alone: all 89 tests passed in 25s. This closes the last item in the original open-items list that wasn't either done or deliberately deferred (Syncthing status integration remains open; the logout-event trigger stays deliberately deferred as untestable from this dev environment).
- **[Decision] WeChat staging topology settled: `staging_path` must be local disk, never a Samba/CIFS mount** — the Samba-testing finding (SQLite can't open a database for writing on a CIFS mount at all) made this a real requirement, not a style preference. This app's own code is unaffected (it never writes SQLite itself), but a live WeChat client's own writes into a Samba-mounted `staging_path` would fail outright. Getting a WeChat machine's local staging folder onto the Debian host is left to something transport-level underneath (Syncthing, rsync, etc.) — the same assumption Hot Data already makes about its own watched folders. `vault_path` has no such restriction; it was verified as a Samba mount, including across two real machines. Documentation-only, no code change, since the constraint only binds WeChat's own client behavior, not anything this codebase does.
- **[Milestone] Syncthing status integration for Hot Data, verified against a real Syncthing instance** — `engine/syncthing.py` queries Syncthing's own local REST API (stdlib `urllib`, no new dependency) for a folder's real sync state, configured per-folder via an optional `syncthing_folder_id`. Installed real Syncthing on the Debian VM, created a real folder via its own REST API, and confirmed `Manager.status()` correctly surfaced `syncthing: idle` in the dashboard row, then confirmed a rescan after a real file write updated the reflected state. Closes the last open build item besides the deliberately-deferred logout trigger.
- **[Troubleshooting] `git pull` on the live systemd deployment transiently 500'd the dashboard — a deployment-process gap, not an app bug** — `web/templates/status.html` was updated (this session, alongside the new Edit routes) to reference endpoints the *already-running* process's Python code hadn't loaded yet, since `TEMPLATES_AUTO_RELOAD` reloads Jinja templates live from disk but never hot-reloads route code. `werkzeug.routing.exceptions.BuildError` on `url_for('edit_hot_data_form', ...)`. Resolved with `sudo systemctl restart sync-manager` (handed to the user, since it needs their password). Lesson for future deployments: **any code update that changes both a template and the routes it references needs a service restart, not just a `git pull`** — the two can desync for the window between the pull and the restart.

- **[Milestone] First real end-to-end use: actual WeChat data flowing through the app, not test fixtures** — WeChat installed on a Windows 11 PC (`C:\Users\DL-Work\Documents\xwechat_files`), paired via Syncthing to the Debian VM: the PC's folder set to "Send Only", the VM's `staging_path` (`/home/dane/wechat-staging`) set to "Receive Only" — a deliberate one-way enforcement in both directions, so nothing synced back from staging can ever reach or corrupt the live WeChat client. Also installed Syncthing on the VM as a proper persistent `syncthing@dane` systemd service this time (earlier Syncthing-integration testing had only run it via `nohup`), matching the same persistence standard as `sync-manager.service` itself. First automatic sync brought over 318 real files (60MB) cleanly. Triggered the first real "Promote now" against actual WeChat data: integrity check passed (`sqlite integrity ok`), atomic promote succeeded into the Samba-shared `vault_path` (`/srv/samba/wechat-vault/vaultdata`), 319 files confirmed present afterward (the extra one is the promotion-state marker), re-verified independently with a direct call to `wechat_vault_integrity_check()`. Auto-promote scheduled every 30 minutes going forward. This is the first time every stage of the pipeline — real WeChat client, real Syncthing transport, real staging, real integrity check, real atomic promote, real Samba-served vault — has operated together on real personal data rather than synthetic test fixtures.
- **[Update] Syncthing status integration extended to WeChat Vault** — same `syncthing_folder_id` pattern already built for Hot Data, now also wired into `wechat_vault` (`engine/config.py`, `main.py`'s `Manager.status()`, both dashboard forms). Closes a real visibility gap: without it, the dashboard's `ok` status only reflected the *last successful promotion* and gave no signal if Syncthing itself had actually stopped syncing staging in the meantime.
- **[Troubleshooting] The `/add` page's two Syncthing-folder-ID fields collided via a shared query-string name** — found via direct browser testing (not caught by the test suite, which posts forms directly and never exercises the GET-prefill/Browse-carry-through path both fields share on the same page). Typing a value into Hot Data's field and then browsing for a path would leak that same value into the WeChat Vault field's prefill, and vice versa, since both read/wrote the identical `syncthing_folder_id` query parameter. Fixed by giving the WeChat Vault form's prefill/carry-through its own `wv_syncthing_folder_id` query parameter (the POST form field itself stays plain `syncthing_folder_id` - no collision there, since only one form submits at a time). The same browser check also caught that Hot Data's own Browse link had never carried its `syncthing_folder_id` through a round trip at all - fixed alongside.
- **[Update] The systemd unit gained `EnvironmentFile` support for secrets** — `SYNC_MANAGER_SYNCTHING_API_KEY` had nowhere safe to live for the deployed service until now; `/etc/sync-manager.env` (`0600`, loaded via `EnvironmentFile=-/etc/sync-manager.env` in `deploy/sync-manager.service`) keeps it out of the unit file itself, which is more broadly readable than a `0600` file. Verified on the real Debian VM: the dashboard's WeChat Vault row now shows the complete picture in one line, e.g. `ok — sqlite integrity ok, size/count within expected range (next auto-promote ...) (syncthing: idle)` - closing the loop the user asked about directly ("i dont have to look at syncthing anymore right?").
- **[Update] One-click "Verify" action added for WeChat Vault** — the user tested the pipeline manually (logged into WeChat on Windows, sent an image to themselves, watched it sync) and asked how to guarantee the Windows and staging copies are identical. `Manager.verify_wechat_vault()` combines Syncthing's own block-hash-verified transfer completion (`needBytes`/`errors` from its REST API - Syncthing already SHA256-hashes every block during transfer, so "0 pending, 0 errors" is a real content-level guarantee, not just a filename/size check) with a fresh `engine.integrity` pass against staging right now, run on demand from a new "Verify" dashboard button, with the result shown inline on the row (`[verified ok @ ...]` / `[VERIFY FAILED @ ...: ...]`). A fully independent cross-machine hash recompute (a script running on the Windows PC itself, trusting Syncthing's math not at all) was considered and explicitly deferred at the user's choice, since it would need new scheduled infrastructure on the Windows machine for a small marginal gain over what Syncthing's own verification already provides. Verified live: clicked "Verify" against the real synced WeChat data (including the just-sent test image) via the dashboard, over SSH from this session - confirmed `verified ok`, no overflow in the Actions column with the fourth button added.
- **[Milestone] Native desktop launcher added (`desktop-app/`)** — the user first asked for the dashboard to be installable as a real app (solved with a PWA manifest/service worker, see above), then explicitly asked for more: a lightweight Tauri/Electron-style app that scans the tailnet to find the right device itself, so there's no URL to remember at all. Built with `pywebview` instead of Tauri after checking the dev machine's toolchain: Rust/Cargo were present but the MSVC C++ Build Tools (`cl.exe`) needed to actually compile Tauri's Rust backend were not, and installing them is a multi-GB admin-rights download. Given the choice, the user chose the zero-new-toolchain path. `desktop-app/launcher.py` shells out to `tailscale status --json`, probes every listed device's `:8420/static/manifest.json` concurrently for the Sync Manager signature, caches whichever IP matches (`~/.sync_manager_launcher.json`) for near-instant subsequent launches, and navigates its native WebView2 window straight to that dashboard. Verified live end-to-end: correctly found the real Debian VM among 7 real tailnet devices by probing (not hardcoded), confirmed the cache made a second lookup take 37ms instead of a full scan, and launched the actual window, which loaded the live dashboard - the user confirmed seeing it. Packages into a single `.exe` via PyInstaller, no installer needed.
